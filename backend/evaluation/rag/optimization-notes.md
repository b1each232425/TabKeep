# RAG 优化方向记录：笔记标题与层级上下文

记录日期：2026-10-10  
状态：暂缓，不改动当前检索与索引逻辑

## 背景

曾考虑在段落的检索文本中补充笔记标题和标题层级，例如：

```text
MySQL > InnoDB 锁 > Next-key lock
它会锁定一个范围，并阻止范围内插入新记录。
```

这样做可能为脱离上下文后主题不明确的短段落补充语义锚点，使向量检索和关键词检索更容易关联到用户问题。面向用户展示的原文、引用内容不需要改变。

## 当前决定

**暂时不实施标题/层级上下文增强。** 当前还没有明确的个人笔记检索案例证明这是实际瓶颈；并且需要先确认现有 Embedding 与全文索引文本是否已经包含笔记标题或段落标题。若已经包含，再重复拼接可能没有收益，甚至增加噪声。

## 适用条件与边界

更可能有收益的内容：

- 段落使用“它、前者、上述方式”等指代，单独看不出主题；
- 正文是术语解释或结论，主题主要由标题表达；
- 多篇笔记正文相似，但标题/章节主题能区分它们。

通常收益有限的内容：

- 段落本身已经自包含，明确写出了主体和术语；
- 当前检索文本已携带相同标题信息；
- 标题只有“总结”“补充”等泛化词，不能提供有效主题线索。

## 若以后重新考虑

1. 先检查实际送入 FTS 和 Embedding 的文本，确认标题、段落标题目前是否已被包含。
2. 找到确实因缺少主题上下文而漏召回的个人笔记案例，再考虑只增强检索用文本。
3. 若实施，保留原始正文用于回答和引用；标题路径仅作为检索上下文，避免引用内容被改写。
4. 评估重建向量索引的时间、存储和一次性 Embedding 调用成本，并检查泛化标题带来的噪声风险。
